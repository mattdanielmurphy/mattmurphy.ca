Coordinator vs open threads

Written 2026-10-31 from your files, your transcripts and Anthropic's current pages. Nothing was changed except this file.

Bottom line

You are right about the shape and wrong about the machinery. "Open a thread for anything" is a better default than "everything goes through a coordinator". But the old setup did not do what you remember, so there is nothing to bring back. You would be building a smaller, better version on top of what Claude already writes to disk.

My recommendation: make every thread a first-class entry point and keep one coordinator as an option you choose, not a layer you must pass through. Total build is about two small threads, and most of the value comes from rule changes that cost nothing.

The biggest find: the Claude app already writes a short status summary after each turn, for most threads, to a local file. You don't need agents to write per-turn summaries, and you shouldn't ask them to. That habit has already died twice.

The extra-message problem mostly goes away by itself. The app only refuses to start a thread on a turn you didn't type on the desktop. If you start threads yourself, the refusal rarely comes up.

What you'd lose is real, though: short replies, one place that says what's waiting on you, and a brain that splits a long voice dump into several threads. The plan below replaces the first two cheaply. The third stays with the optional coordinator.

This reverses your own decision from Oct 29 ("hooks empower coordinators, never replace them"). Your newest word wins, but you should make that call knowingly.

What the old setup did

What it actually was

  • preflight.py: a script the agent had to choose to run. It checked Antigravity quota, rebuilt rules if stale, scanned for secrets, ran git pull, started the watcher, checked Hammerspoon errors, and printed recent threads and the project board.
  • watch_transcripts.py: a background daemon that checked Antigravity transcript files as often as every 50 milliseconds. It rendered Discussions.html, ran the evaluator, auto-committed after each finished turn, and started a summary after five idle minutes.
  • summarize_thread.py: sent the first request and final reply to DeepSeek through the local LiteLLM proxy for a two-sentence summary, saved in thread_summaries.json.
  • transcript_evaluator.py: checked replies for banned HTML tags and estimated length.
  • Agent logs and journal rules: at the end of a session, write agent-logs/<date>_<topic>.md in the project and add 2-3 lines to DEVELOPMENT_JOURNAL.md. New sessions were told to read those first.
  • Git rules: run preflight first, commit and push when done.
  • Gemini rules: treat preflight output as system-level instructions, plus cleanup rules for subagents and background tasks.

It read Antigravity from three folders (~/.gemini/antigravity, antigravity-ide, antigravity-cli), each holding brain/<id>/.system_generated/logs/transcript.jsonl. It sorted by file time, took the first typed line as the title, pulled project names out by pattern, and linked subagents to parents by finding their ids in the text. It never read Claude's transcripts, not once.

Where your memory is rosier than the evidence

"It ran at the start of every turn." Mostly no. Since Aug 15 the rule said once per thread, turn 1 only. A separate every-turn step (postflight) lasted two days for Gemini, Aug 13-15, because it added latency. The Claude version of that rule did exist until it was shelved on Oct 17. The log shows 996 finished runs in three months, against roughly 3,400 Antigravity thread folders (many are subagents). So it depended on agents remembering. A hook can't forget, which already makes today's version stronger.

"It found similar threads." No, never. It printed the 8 most recent threads by first line and folder. It wasn't even given your prompt, so it couldn't compare anything. Your current recall hook, weak as it is, does more than preflight ever did.

"Agents wrote summaries every turn." No. Agent logs were per session, and only when code changed. Thread summaries came from the watcher, not the agents. thread_summaries.json was last written Aug 13, so summaries stopped within about a day of being built, and nobody noticed. Preflight kept a fallback line for missing summaries until the feature was removed on Sep 16.

"It was self-improving." The evaluator logged 2,046 turns and found 5 problems, all HTML tags. It flagged bloat zero times. Its six "synthesis reports" have identical findings because the text is hard-coded: they always say no rule drift was detected.

"It was cheap." Not really.

  • The Gemini rules file is 13,714 words, loaded into every thread.
  • 1,785 of your 2,969 ai-os commits have generic messages, and 1,251 commits touched Discussions.html.
  • One auto-commit swept in 5,379 files and 4.1 million lines, including compiled cache files.
  • July audits show you were already fighting quota waste, for example 1.27 million cumulative context tokens in one 146-step thread.

Why it was really abandoned: not because the shape failed. The shelf says the Antigravity trial ended with quota near zero, and the proxy, DeepSeek and Hermes went with it on Oct 17. The whole system was tied to one vendor's file paths.

What the current one does

The moving parts

  • Central Coordinator: a pinned session that splits your messages, picks folder, model and effort, starts or reuses threads, relays results, archives finished threads, and takes voice tasks.
  • Project coordinators: one per project (Glass TV, Slub), plus subject coordinators started automatically when two threads share a subject.
  • Advisor hop: big asks go to a sub-coordinator that writes a plan, which the coordinator then carries out.
  • Registry: a hand-kept list of threads, to be updated every turn.
  • Hooks: seven on each prompt (recall, habit gate, big-prompt guard, rule nudge, worker feed and others), plus guards on tools, sends and turn end.
  • Mods: action bar, context alert, read-aloud, no-suggestions, visible session.
  • Daily custodian: a job that drops a prompt into the Coordinator for clean-up, loose ends and due dates.
  • Recall: Claude transcripts are exported to markdown, indexed by QMD, and each prompt gets up to four keyword-matched pointers.
  • Details files: one per thread, published as Readthroughs.

What the numbers say (Oct 28 to now)

  • You do go through it. 530 of your 566 typed messages went to coordinators, only 36 directly to workers.
  • It is expensive. Coordinators are 5 of 164 sessions but about 32% of model use, and 1.04 billion of the 2.9 billion cached tokens read. That uses rough API price ratios, so your plan's meter may differ. Each message to a coordinator costs about 35-90% of what a median worker uses in its whole life.
  • It is not slow. Median time from your message to a thread starting is 13 seconds, 90th percentile 52. Speed isn't the real problem; friction and cost are.
  • Its context never stays small. The current central session compacted 30 times in about 32 hours. Each one is a chance to lose detail, which is probably part of why it feels clunky. The previous one ran at a median of 338k tokens.
  • Starts fail often. 36 of 229 start attempts were refused (16%).
  • The registry has quietly stopped. Last updated Oct 28 20:22, with 36 entries against 164 active sessions, even though the doc says to update it every turn. The system depending on it hasn't noticed. That's the same way the old summaries died.
  • Worker feed is too new to judge. Four messages queued, none flagged.

Recall, tested

I ran four realistic prompts through the recall hook. One gave clearly useful hits. "Make a new explainer reel about the rules plan" missed the actual thread with that name, and two others returned loosely related files.

Two reasons stand out. Of the 549 exported "threads", 122 are read-aloud one-shots and 289 are titled by a relay prefix, not a topic. And it only ever knows what was exported up to 15 minutes ago, with no idea whether a thread is running or finished. So it can't tell you another thread is working on this right now, which is the thing you actually want.

What the old setup did better

Mainly one thing: no middleman. Every thread was equal, and it stayed vendor-neutral plain files. The agent logs also gave you a readable project history, which details files now provide.

What the coordinator does better

Honest credit, because these are real:

  • Replies you can actually read, at half the length of workers'.
  • A single place to dump a long message and have it split up.
  • Choosing folder, model and effort without you thinking.
  • Checking a thread's claim before telling you it's done.
  • Cleaning up finished threads.

What's a real platform limit vs your own choice

Real limits, you can't change these:

  • A thread can only be started on a message you typed in the desktop app. Refused cases are another session's message, an automated or plugin-sent turn, and a brief given by another session.
  • On Remote Control the app refuses too. Its refusal message suggests this is temporary, so it may change.
  • A proposal card can't carry a folder (14 of the refusals).
  • A hook can add context or block, but can't move your message into another thread.
  • A new thread's effort and model can't go above the parent's.
  • Sessions can only see other desktop sessions, not cloud or terminal ones. By default it lists the 20 most recent.

Please don't engineer around the start rule. It exists so sessions only begin on your own words. The sanctioned phone route is Dispatch, or Remote Control's server mode, which creates sessions from your phone. Neither has been tried on your setup.

Self-imposed, all changeable by rule:

  • Everything through the coordinator.
  • Automatic subject coordinators at two threads.
  • "No analysis in the coordinator", which forces another hop.
  • The advisor hop for 500+ word messages.
  • The hand-kept registry.
  • Running the coordinator at low effort, which also caps what it can start.

One thing in your docs is wrong. The big-prompt hook says sessions started by a session can't start threads. They can. Both the central and Glass TV coordinators were started by sessions, and they started threads fine whenever you typed to them. The block is per turn, not per session. That matters: you can type "split this into three threads" in any desktop thread, and it should work.

Recommendation

Yes to "every thread is a first-class entry point; the coordinator becomes optional". No to reviving preflight, the watcher or agent-written per-turn summaries.

Step 1: rule changes, no build

  • Any thread is a valid starting point. The coordinator is something you open when you want it.
  • Stop automatic subject and project coordinators, and drop the advisor hop.
  • Stop treating the registry as required. The app already knows this.
  • Raise your default effort. Your settings default is low, so threads you open yourself would start low on real work. Medium is the likely right default.
  • Remove the dead preflight, journal and agent-log rules, as the rules-to-hooks plan already proposes.

Step 2: a real "similar threads" check, one small thread

A small background job, run about once a minute, reads the app's session files and writes one compact list: title, folder, last active, status, needs-you. On the first prompt of a thread, the recall hook compares your words with that list and adds up to three lines, such as "an active thread may overlap: X, status Y".

This is what you remember preflight doing, and it would be the first time it has existed. It needs no model calls and adds about 100-150 tokens per new thread. A background job is needed because reading all 406 files takes about 2 seconds, too slow for a prompt.

Step 3: clean recall, part of the same thread

Exclude one-shots from the export and use real thread titles. Without this, the hook's hits stay noisy.

Step 4: a "waiting on you" list, one small thread

Show threads the app marks as blocked or needing action, from the same list, in an existing panel or HUD. No tokens. This replaces most of what you'd miss from the coordinator's status messages. Add a heartbeat line so it can't die silently the way summaries and the registry did.

Step 5: move the custodian

It currently needs the Coordinator to receive its prompt. Make it a desktop scheduled task so it runs either way. Keep its archiving and due-date checks.

Step 6: try it for a week, then decide

Watch duplicate threads, weekly usage, and how often you still open the coordinator. If duplicates pile up or you miss it badly, you've lost nothing, since it's still there.

Keep one coordinator for

Long voice dumps, big multi-thread projects like Glass TV while they're hot, and phone messages into existing threads. Open it deliberately.

Cost and what breaks

Build: two small threads, plus an hour of rule edits. No new projects, so it fits the freeze, and it simplifies overall.

Usage saved: I'd expect most of the coordinator's third to go, perhaps a quarter of total use. That's an estimate, untested, and some of it will come back as you open coordinators when needed.

What breaks or gets worse:

  • Longer replies. You'd read workers directly, at twice the length. The rules-to-hooks plan's reply-length check matters more now. This is the biggest day-to-day downside, especially since you listen to replies.
  • Duplicate work. Step 2 reduces it but won't eliminate it. Two threads editing the same repo can still collide, which was only ever partly handled.
  • Wrong folder. You pick it when opening a thread. A thread started in the wrong one has broken your links before.
  • Model choice. Nobody checks your usage pace for you. A short line at thread start can state it.
  • Undocumented file. The app's session files aren't a public format, and Anthropic warns transcript formats can change on any release. If it breaks, the hook must fail silently and you lose only the overlap hint.
  • Voice tasks. Plugin-sent turns can't start threads, in either world. That's already true today.

Things you should not build: agent-written per-turn summaries. The agent logs died, the details ritual has faded (57 new files on Oct 22, one to three on most days this week), and each summary means an extra model call that re-reads the whole thread. The app's summaries cost your agents nothing. Whether they count toward your plan isn't documented, and I couldn't measure it.

Timing is good. The rules-to-hooks plan is still waiting on your go for step 0, and its coordinator steps (role packs, judges) would be built around the design you're now questioning. Decide this first, and those steps shrink.

Slub overlap. The Oct 28 idea of a Slub coordinator for you and Tyler in slub-hq IDEAS.md depends on this choice. Tyler should hear about it.

What Claude keeps on disk

Yes, the same idea as Antigravity, and better.

  • Where: ~/.claude/projects/<folder>/<session-id>.jsonl, for terminal and desktop Code sessions alike. You have 625, 1.36 GB, of which 595 are desktop. None predate Oct 17, and I couldn't establish why.
  • Live: yes. Anthropic documents continuous saving, and I confirmed it: this report's own transcript was 11 seconds old when checked.
  • Complete: yes. Your messages, replies, thinking text, tool calls and results, and records of what was sent to the model. Compaction doesn't erase earlier lines. Subagents sit in a subfolder and big tool outputs in another.
  • Kept: your retention is set to about 100 years, and desktop transcripts are kept at any age by default anyway.
  • Plain text: not encrypted. Anything a tool prints lands there.
  • Caution: Anthropic says the format is internal and can break on any release. Their suggested routes are export, hooks that receive the transcript path, and claude -p --resume.

The extra file that matters: ~/Library/Application Support/Claude/claude-code-sessions/…/local_<id>.json. There are 406, linking the sidebar id to the transcript, with title, folder, model, effort, archived state, who started it and last activity. 322 hold a postTurnSummary with a status and what's needed from you, and 81 hold a report of the last turn. This is the free per-turn summary. It's undocumented.

Native tools exist too. Any desktop thread can list sessions and search all transcripts. Those cost a model call each, so they suit deliberate searches, not every prompt.

Claude.app chats and Projects threads: not usable on disk. They live on Anthropic's servers. A simple search of the app's local database found no message content, though that database may be compressed, and the roughly 1 GB web cache has only scattered fragments. Cloud sessions are also remote. The Mac-side worker of a Projects thread was local, but the cloud coordinator's conversation was not. That's why pull_voice_chats.py has to fetch from claude.ai.

Short answer

Yes, you can build a personal frontend on your subscription with no API bill, as long as it drives the real, unmodified claude program signed in through Anthropic's own login. It uses your normal plan limits, so it saves no usage. You can't give that to others on your subscription, and you must not lift your login token to call the API directly.

How far it goes

claude -p is documented as the Agent SDK's command-line form. It's close to the whole engine: tools, permissions, hooks, skills, subagents, MCP, plugins, resuming a session by id, streaming JSON events for live text, and structured output. That's enough for a real chat UI.

What you wouldn't get: desktop-only tools like session starting, the sidebar, and mods, since those belong to the app. -p sessions stay out of the normal resume picker. A long-lived token from claude setup-token can't do Remote Control or fetch claude.ai connectors.

Watch this one. Anthropic's docs say --bare will become the default for -p in a future release, and bare mode ignores subscription login. Your hooks using claude -p (worker feed, cold handoff, Tab Tidy) could stop working, or switch to an API key if one is set. Check this when Claude Code updates.

What's explicit policy

Subscription vs API key:

  • claude -p and the Agent SDK signed in with your plan draw from your plan limits. That's stated, and it means this use is permitted and metered.
  • Plan limits are shared with Claude chat and Code: five-hour and weekly on Max.
  • With ANTHROPIC_API_KEY set, -p always uses the key and bills API rates. There's a key in your ai-os .env, so a script that loads that file before calling claude -p pays real money.
  • The Jun 15 plan to split Agent SDK use into its own credit is paused, with no stated end. It could return.
  • Since Oct 7, Max includes $100 a month in API credits. It covers -p and the Agent SDK only with an API key from a linked Console organization. It doesn't roll over, and interactive Code isn't covered. If you're on Max as your notes suggest, this is free money for background jobs.

Limits on use:

  • Consumer Terms bar access "through automated or non-human means" unless by API key or where Anthropic explicitly permits it (section 3). The -p documentation and plan-limit statements read as that permission for Claude Code, but they don't say so in those words. That reading is my inference.
  • Advertised limits assume ordinary individual use of Claude Code and the Agent SDK.
  • Subscription login is intended for ordinary use of Claude Code and Anthropic's native apps.

Third parties and developers:

  • Developers building products or services, including with the Agent SDK, should use API keys.
  • Third-party developers may not offer Claude.ai login or route requests through plan credentials for their users, and may not collect or store Claude credentials or session tokens.
  • Anthropic may enforce this without notice.

Distributing to others:

  • Preinstalling or running Claude Code in a product requires the Commercial Terms and an unmodified binary.
  • Each end user must sign in with their own key or plan, and you can't pay for or resell their use.
  • Your product can't use the Claude Code name or look. The Agent SDK note adds that offering claude.ai login needs prior approval.
  • Consumer Terms section 2 bars sharing your login, and section 3 bars building services that compete with Anthropic's. A public chat frontend gets close to that second line.

What separates programmatic use from "what I'd have typed"

No Anthropic text I found draws that line. A forwarded message and a scripted one are the same -p call on the same meter. The lines actually written down are about credential, who runs it, on whose behalf, and ordinary use.

My inference, not policy: forwarding is the safest position, because one human message produces one turn, at human pace, by one person. That is ordinary use by any reading. Risk rises as prompts stop coming from you: per-message Haiku checks, watchers, cron loops, always-on agents. Risk rises sharply if volume looks like a service rather than a person.

Your options, safest first

  1. Mods inside the app. First-party extension point, and you already use them.
  2. Personal UI driving the unmodified claude program, on your Mac, for you only. Fine in my reading. Keep automation modest.
  3. Background jobs on the Max API credit with a Console key. Cleanest for automation, since API keys are the explicitly allowed route.
  4. Sharing with Tyler. He runs his own install with his own login. Never your account or token. Grey if it becomes a packaged product.
  5. Selling or publishing it. API keys or each user's own login under Commercial Terms. Ask Anthropic sales first.

Don't do: extract the OAuth token, proxy it, disguise a client as Claude Code, or modify the binary.

One existing thing to look at: pull_voice_chats.py reads claude.ai's internal API through your signed-in Chrome every night. It's read-only and your own data, but on its face it's the automated access the Consumer Terms restrict, and I found no permission covering it. The practical risk is probably low, but your connector's save_call path, with a lighter fallback, would be cleaner.

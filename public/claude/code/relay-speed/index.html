Relay speed: making Mattinee start like Stremio

16:45 Why the relay path swings, and the fix

You asked for the relay path to match Stremio without ever going direct to Real-Debrid. The cause is found and the fix is one command, not yet run, because it changes the live VPS. All tests were this afternoon, with your Ted Lasso paused.

The cause is cubic on the VPS

The VPS sends with cubic, the default way TCP decides how fast to go. A little packet loss on the way to your Mac makes cubic slow right down, and on an 85 ms path it stays down for the whole connection. That is your 1 to 2 Mb/s. Your live paused stream showed it: send window 14 packets, slow-start limit 7, about 1.7 Mb/s.

BBR is another way of deciding speed that doesn't treat every lost packet as a reason to slow down. Google uses it. It was already on the VPS as a kernel module.

Which route each device uses

  • Mac: times both routes at each play, keeps the result 10 minutes. Its own log shows the VPS picked 3 of 3 this afternoon (direct 0.1 to 7.4 Mb/s, VPS 12 to 30). So the chooser works and the last plays were on the VPS route.
  • iPads and Streamers: always direct to the mini PC. There is no route choice in those apps. In Ft Sask that is the home network and fine.
  • Edmonton and Ontario iPads: same direct path that collapses for the Mac, sent by Windows 10, which has no BBR. Not measured from those devices; inferred from the Mac.

What I ruled out

  • Tailscale relay servers: every path is direct, not going through DERP. The first ping after idle goes via Seattle, then direct.
  • The Real-Debrid server: sea1-4 and sea2-4 are equal, and links land in Seattle for both homes.
  • Relay code: 73 Mb/s out of the mini PC through the real relay. Buffers and chunking aren't the limit, so I changed nothing there.
  • The gate: it gives up early on a slow copy, but the copy was only slow because of cubic. Left alone; expect far fewer fallbacks.
  • Song pack named Season 1: didn't affect tests, which used the public file.

The change

deploy/bbr.sh turns on BBR for new connections on the VPS and keeps it across reboots. Nothing restarts, running streams stay as they are, deploy/bbr.sh undo reverses it. It prints three speed reads when done.

Rejected: tuning Windows (Windows 10 has no BBR, and the VPS route already avoids that sender). Rejected for now: fetching ahead onto the VPS, since it isn't needed at 60+ Mb/s.

Untested and risky

  • No real play yet. The tests used Real-Debrid's public file, so first-picture time on a real play is still to be measured. Expected: a few seconds, since 60 Mb/s fills a 5 Mb/s copy quickly. Opening took 2.8 s on the last play and isn't touched by this.
  • Evening load. All numbers are from about 16:30. The mini PC upload at busy times is unmeasured with BBR on the VPS, because BBR can't fix that leg.
  • The Bun hop itself hasn't run under BBR; the test used a Python copy of it. The script's speed reads cover that.

Other findings

  • Idle connections: the relay is holding about 100 open connections to Real-Debrid, some 16 hours old, and 99 half-open sockets. Speed didn't suffer with them there (84 Mb/s). Likely idle ones from link checks. A restart clears them; worth a fix in relay/relay.ts some time.
  • Mac packet drops: the Mac dropped 117 Tailscale packets during the tests because its receive buffer filled. It also runs Little Snitch, AdGuard, TripMode and the PIA extension on the network path. That may be where the loss comes from. I didn't touch system settings. BBR copes with it.

What I did outside the plan

  • VPS: loaded the BBR kernel module and allowed it, so my test port could use it. The default stayed cubic, and scratch test programs are removed.
  • Test reads ran long: five test reads ran the full 20 seconds, 200 to 290 MB each, because the public file ignored my size limit. They were spaced out, and later reads were capped by time. No account link was touched.
  • Mini PC: two small read-only scripts, deleted afterwards.

To undo: deploy/bbr.sh undo once run. To drop the BBR module, nothing is needed; it does nothing unless selected.

17:20 The fix for every client, and Linux on the mini PC

You said BBR made it so much better and that all clients need it, then said you'll install Linux on the mini PC.

BBR is live and the first play proves it

The VPS is on BBR and live connections show it. Your 16:09 play on Ted Lasso started in 6.5 seconds with no fallback, against 35 to 57 seconds this afternoon. That's one play, so it isn't an evening average yet.

All clients through one server change

iPads and Streamers never used the VPS route, because only the Mac app had a route chooser. The server already knows where each viewer is, so it now hands anyone outside Ft Sask the VPS address. Nobody needs a new app. In Ft Sask they stay on the home network, since a trip to the VPS and back would only be a detour. Unknown places get the VPS.

The speed test follows the same route, so a screen measures the line it will really use. If the hop stops answering, which it also does at its 8 TB monthly limit, viewers go back to direct. Checked every 15 seconds when someone plays.

Mac plays still use the app's own timing, so the Mac server is unchanged. Rejected: a route chooser in each app, because it would need builds for iPad and Android to do what the server can do alone.

Tested and not tested

All 5 new tests pass, and the full test run is in the commit. Tailnet rules let every device reach the hop. Not tested on a real iPad or Streamer: the change isn't live until the restart. Android and iPad work out the relay address from the link, and the hop answers the same checks, so they should behave the same.

Linux

Good idea, and no rush now. Linux can send with BBR, which Windows 10 can't, so homes may be able to skip the VPS entirely. It would also speed up Tailscale. Whether direct then works as well isn't proven until it's running. While it's down, nobody at either home can watch, because the VPS's way out goes through it. Recorded in IDEAS.md.

Only the relay, Tailscale, the metrics exporter and Jump Desktop run on it, so nothing else needs moving. Secure Boot is on.

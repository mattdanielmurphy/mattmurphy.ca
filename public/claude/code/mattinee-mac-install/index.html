20:50 Cursor lag and window dragging

You said the cursor was remarkably laggy, and that dragging in the middle still moved the window.

Why the cursor lagged

The video draws on the app's main thread and slept there until each frame's moment. Mouse events reach the page through that same thread, so they arrived in bursts at the film's frame rate. Fix: the video no longer sleeps there (video-timing-offset=0, no blocking in the render call). The page's check of what's near the mouse also forced a full layout on every move; it now refreshes every 120 ms (PLAYER.middle.fieldEvery). Neither fix has been felt yet, and the first is a likely cause, not a measured one. If some lag remains, the fallback is a real system cursor drawn from the leaf.

Window dragging

Dragging the picture no longer moves the window; the setting and the old drag code are gone. Windowed, a toolbar strip runs along the top: it shows when the mouse reaches it, moves the window, and a double click zooms. Full screen has no toolbar.

Testing

Headless page checks pass. Real mouse testing is yours. Run with --glass-trace=1, and the page writes how late the mouse arrives, once a second, to tmp/gp.log.

Earlier I closed the test window while rebuilding, which may have been while you were using it.

21:20 Choppiness and Low Power Mode

Your run's numbers: the mouse reached the page about 5 ms late, so the first lag fix worked. But frames stalled about 35 ms even with the mouse still, which is a 30 frames a second cadence. WebKit limits web page animation to 30 frames a second in Low Power Mode, so your finding fits the numbers. It's untested until you run it with Low Power Mode off.

I left the setting alone: changing system settings is something you have to do yourself.

Next, if it's still not 120 Hz with Low Power Mode off

  • WebKit also caps pages near 60 Hz by default. There is a private setting, _preferPageRenderingUpdatesNear60FPSEnabled, to lift that.
  • The video still draws on the main thread. Moving it to its own queue, as IINA does, frees that thread, but it touches code the move-up work depends on.

21:55 HDR on the Mac and your Sony TV

You said HDR looks like a dimmer normal stream, and asked whether the app needs a setting. Both of your suspicions were right.

What was wrong

The player had no HDR output at all. It drew into an 8-bit surface with no HDR request, so mpv squeezed every HDR film down to normal range. That squeeze is the dim look. "4K · HDR" in the logs only describes the source file.

Your Sony also reports no HDR range to the Mac right now (maximumPotentialExtendedDynamicRange 1.0), because High Dynamic Range is off for it in Displays. The laptop screen reports 16. No app can send HDR to the TV until that setting is on, and an app can't turn it on.

What changed

On branch claude/mac-hdr, not yet on master. The player now uses a 16-bit float surface and, when the film is HDR and the screen can show it, sends the picture as PQ with BT.2020 and asks macOS for extended range. If the film is HDR and the screen can't, it says once: "HDR film. Turn on HDR in Displays to see it". It rechecks when the setting changes or the window moves screens. --glass-hdr=force is a test switch.

Rejected: leaving HDR on all the time for the TV, because it dims the desktop as you saw. Auto-switching the TV's HDR for you would take a private system call or a tool like BetterDisplay, so it's a separate idea, not built.

Risks

Dolby Vision-only files may still look wrong: this player path has no Dolby Vision support, which is a limit of mpv's older renderer. X-ray's paused frame is now PQ-tagged while HDR is on, and the server's face matcher may see it paler. Not tested on your TV: only your eyes can confirm that.

22:05 Correction: is the Displays setting really required?

You asked if I was sure. I wasn't entitled to be. I measured that your Sony reports no HDR range with the setting off, then said no app could send HDR until it's on. That second part was my assumption.

Apple's page says a Mac "might automatically enable HDR" for a display, while a forum report says macOS doesn't switch. They disagree, so only a test on your TV settles it. My code also only asks for HDR when the screen already reports range, so it could never have triggered a switch. The test forces the request on a short visible clip and watches the TV's range. Your Netflix memory fits the laptop screen, which reports range 16 with no setting at all.

If the TV doesn't switch by itself, the Displays setting doesn't have to stay on: BetterDisplay has a command-line tool that could turn HDR on for an HDR film and off afterwards. I haven't confirmed its exact HDR command. The dim desktop in HDR mode looks real: reports say macOS has no balance slider for it.

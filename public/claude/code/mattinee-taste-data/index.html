21:35 Taste data, server side

You asked for tracking now, with a Netflix-style love, like, dislike or hate question at the end, per profile, so a recommender has data later.

The server side is built, tested and pushed. It is not live yet, because someone was watching when it was ready.

What is built

  • A permanent record per person. It keeps what was started, when, how far it got, whether it finished, how many times, and the rating.
  • It needs no app update. It is written from the reports the players already send.
  • Ratings work. Love, like, dislike, hate, skip, change later, take back.
  • The rule for asking. One server answer, so every screen behaves the same. No app asks yet.
  • Seeing it. bin/taste, bin/taste family, and /taste in a browser.

The contract is in docs/taste-contract.md in glass-tv.

Decisions and why

  • Its own files, not state.json. state.json is rewritten every few seconds, moves between files when the Mac switches person, and isn't the same file on every server. taste/<profile>.json is one simple file per person.
  • Capture at the server, not in the apps. Every client already reports progress, so old builds count from day one.
  • Sittings worked out on the server. Three quiet hours starts a new one. Rejected: a play id from each app, which would need new builds everywhere.
  • "Gave up" worked out on reading. Unfinished and untouched for 14 days. Stored, it would be wrong the moment someone came back.
  • Time really played is kept. Skipping to the end flips the app's finished flag, so this is how a recommender can tell.
  • Carried on the existing sync round. A merge only adds, and the newest rating wins, so a resend can't lose or double anything. Rejected: forwarding like the play log, because a rating made while the VPS is away would be lost.
  • Stable id is the IMDb id. The existing progress key is only the title, so two films called Dune would collide.
  • The rule for asking lives on the server. Tweaks are taste.askStoppedMinutes and taste.askShowEpisodes.
  • Not built: Continue Watching removal, Library adds, and Trakt or Letterboxd history as signals. They are in IDEAS.md.

Backup

I found no backup of the VPS data folder: no cron job, no timer, nothing in the deploy scripts. The taste files are now copied whole to your Mac by the sync round, as long as the home Mac server runs the new code, and every server keeps 30 days of dated snapshots.

Everything else in that folder, such as progress and Libraries, still has no deliberate backup. It only survives through the sync copies on the Mac servers. That is outside this job.

What was tested

  • 21 taste tests pass. They cover sittings, ratings, the ask rule, merging, backfill and the endpoints.
  • The full suite has one failure, tests/addons.test.ts, which also fails on the commit before this work.
  • Two real servers on a copy of your data. Backfill gave 19 titles for you, and 8 profiles in all. A rating made on a Mac-side server reached the main one and a change came back within one sync round. A second server backfilling the same records made no duplicates, and every record found its IMDb id.
  • The test copies of the data were deleted afterwards.

Not seen on a real play: Mac, iPad or the Streamer. The Mac line in saveProgress was type-checked but never run by a real player, because that needs the new code live.

Deploying

Order doesn't matter: an old server ignores the new sync field. deploy/mac-people.sh skips anyone watching, so they stay on old code until the next run.

How to undo: put back the previous commit and redeploy. The taste files stay where they are and do nothing.

More

The first run writes one backfill per person per server, recorded in taste-sync.json in the data dir. Sittings from backfill have the id backfill:<thing id>, the same on every server, which is why two servers can't double one.

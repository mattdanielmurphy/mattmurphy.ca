Mattinee: SDR under system HDR, and scroll volume

What you asked

  • Normal films looked washed out and too bright with HDR on for the Sony, while YouTube looked fine. You wanted a treatment for SDR, not HDR switching.
  • Unmap scroll for volume in the Mac player.

The cause

Our picture reached macOS with no colour tag, and an untagged picture gets no colour conversion at all.

Measured numbers

I sent the same clip through the real pipeline and read back the light that came out, where 1.0 is normal white. The clip was a short test I made, 8-bit H.264 tagged BT.709, like Ted Lasso. Nothing was shown on a screen, and nothing played aloud.

Input level QuickTime path Mattinee before Mattinee now
0.10 0.011 0.102 0.011
0.20 0.043 0.200 0.043
0.50 0.259 0.502 0.259
0.80 0.645 0.800 0.646
1.00 1.000 1.000 1.000

The biggest gap from the QuickTime path across 12 greys and 6 colours fell from 0.243 to 0.009. Shadows at level 0.1 were nine times too bright, and mid grey nearly twice.

Why only with HDR on

With no tag, macOS passes the values through untouched. On a normal screen that is fine, because the screen applies its own gamma. With HDR on, the Sony is mixed in light, so a film value of 0.5 lands as half of white. This part is inference: the renderer I measured with was writing to a linear target, and I can't read the light at the Sony's glass. It fits your screenshot and fits why YouTube was fine, since video frames arrive tagged.

The 16-bit surface was not the cause

The surface added with HDR output in b6d1a36 was a suspect. It wasn't guilty: the old 8-bit surface measures the same as the float one when untagged. So normal films have probably looked like this any time HDR was on for the TV.

The fix

Tagging the picture

On an external screen showing HDR, a normal picture now carries a tag: BT.709 colours with a 1.961 gamma. That is the curve macOS gave a real decoded BT.709 frame. mpv's output is unchanged, so this is correct tagging, not a brightness tweak.

Why not the stock BT.709 tag

I tried it first. It matched in the mid-tones but kept about twice the light in the shadows, 0.023 against 0.011 at level 0.1. Shadows were part of your complaint, so I built the exact curve instead. sRGB was too deep against QuickTime, so that is now knob value 2.

What stays the same

  • HDR films: still PQ, same path.
  • Laptop screen: untagged, as today. It always reports range, so the check excludes built-in screens.
  • Screens without HDR on: untagged, as today.
  • X-ray's paused frame: reads the same values as before, because only the tag changed.
  • Moving between screens: the existing screen-change hooks now update the tag too, and a paused picture redraws.
  • Move up to 4K: the second picture gets its tag before the cross-fade, so it can't flash bright.

The knob

player.sdrOnHdr: 1 matches QuickTime and Safari, 2 is a little deeper, 0 is the old untagged look. The player defaults to 1, so it works even where the server doesn't pass the knob. Beta uses the VPS server, so 1 is what you get there until that server is updated.

Scroll volume

Removed the wheel handling on the picture in the player, and the one on the page. The volume tooltip and README no longer mention scroll. ↑ ↓ and the pill still work. The mock had no scroll volume. Other wheel behaviour, such as sideways lists and the recap panel, is untouched.

Untested, and risks

  • Not checked on the Sony's glass. Measurements ran through Core Animation's renderer, the same engine macOS uses, with no window. Only your eyes settle the final look.
  • Not run in the real app. It compiles, and the same screen check gave the right answer on both your screens: Sony tagged, laptop untagged. Running it would have put a window on the Sony while you were watching.
  • A real screen capture wasn't possible. Capturing a hidden off-screen window hung, so I dropped it rather than show a window.
  • Other HDR-capable external monitors get the tag too. That is correct colour, just a change from before for those screens. You have none.

How to undo

Set player.sdrOnHdr to 0 where the server passes it, or revert the commit.

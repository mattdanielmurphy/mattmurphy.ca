Mac app on TestFlight: feasibility

Findings (from reading the code; nothing built or changed)

Sandbox is fine

Only spawnServer (app/main.swift) is forbidden, and a VPS build skips it. Needs: outgoing network, microphone entitlement, plain-http exception for 100.x, and all 48 Homebrew libraries behind libmpv copied into the app and signed. Hardened runtime is not required for TestFlight, only the sandbox. Not yet spiked.

The real blocker is not the sandbox

The Mac app is a shell around the server's /api. That API keeps one global person and one "now playing", and the server tracks time through mpv's unix socket on its own disk (src/player.ts). On the VPS that socket doesn't exist, so progress would not save, and all Macs would share one profile and one now-playing. 127.0.0.1 is also hard-coded in app/main.swift, app/browser.swift and app/player/core.swift.

Options

  • A, recommended: new Mac target using the iPad screens (per-person /tv/v1 already works on the VPS) with the Mac mpv player. Local build untouched, no server change. Loses web-only extras such as the tonight plan.
  • B: rework /api per person and report time over HTTP. Keeps the current UI, but is a large, risky change to the shared server.

App Store Connect

Same bundle ID means the Mac build must use ca.mattmurphy.mattinee.ipad; local stays ca.mattmurphy.mattinee, so both can coexist. macOS must be added as a platform to the record, possibly by hand. As I recall, Apple stops offering the iPad-on-Mac version once a native Mac build exists; not verified.

23:30 Real Mac app on the VPS

What changed

You pointed out that one VPS process per person avoids the shared-profile problem, so the earlier iPad-screens recommendation was dropped. Each person gets a server under /srv/glass-mac (ports 4801-4806), and a small door on port 4800 lists them. Progress and Library sync with the main server. The app carries the player's time to its server over a WebSocket. The main server was not restarted or changed.

Test result

A sandboxed debug build, muted and hidden, started a stream through the relay: 4.88 seconds played, then position showed no change on the last poll. Not proven to keep playing. Your first try stalled because I closed the app and restarted its server while you were using it.

Upload

The upload reported success. It has not been confirmed as visible in TestFlight. Needs macOS 15+ and Apple Silicon. Unit tests: 50 of 51 test cases passed with one rating-filter failure, and a local-port listen error appeared in this environment; neither was checked against the previous commit. X-Ray and song ID are untested on this build.

23:50 Picker moved to your own screen

Removed the app's dialog and its Go menu item. Before anyone is picked, the app opens the first person's server to show Who's watching; picking moves the app to that person's server and remembers it. Switch profile in Settings works the same way. "Don't ask me again" carries over. Not yet tried in the app.

23:30 Why it buffers

Relay process IDs from metrics: a new one almost every minute from 23:07 to 23:27, with memory up to about 2 GB. The current relay started at 23:27. The mini PC downloads 100-440 Mbit/s but sends only 2-14 Mbit/s, peak 34 this week, so it pulls far more than it delivers. This started before my Mac servers (23:11), which corrects my earlier suggestion that they were the likely cause. The fix is commit 05f0356 (watchdog and bounded memory). It is not live: the update refuses while anyone streams, and forcing it cuts current streams. Upload capacity with the fixed relay is unmeasured. Real-Debrid's terms were not checked here.

23:55 Link measurements

Blank test data from the relay: Mac 2.5 Mbit/s per connection, four connections about 10 total; VPS 142 Mbit/s. Mac direct internet 103 Mbit/s. Mac from VPS over Tailscale with ssh 7.1 Mbit/s. So the mini PC upload is not the limit for this path. Suspects are the path into this Mac over Tailscale: Little Snitch, AdGuard, the PIA split tunnel and TripMode are all active filters here, or UDP handling by the network. Turning those off is your call, not mine.

00:15 Why the link is still slow

Filters were ruled out by you for Little Snitch. No packet loss on small-rate pings, latency steady under load, Wi-Fi strong, 5 GHz. Regular internet to US servers at about 300 ms: 45-52 Mbit/s, so the Mac copes with distance. 3 MB transfers: mini PC to Mac 5-11, VPS to Mac 19-27, mini PC to VPS about 40 Mbit/s. Rejected: mini PC upload, Mac TCP settings as a general limit. Likely: the direct home-to-home Tailscale route. Exact cause unproven; short samples include TCP ramp-up. Proposed: test mini PC to VPS to Mac on a tailnet-only test port, without touching the main server. A temporary test file server was blocked by the permission system and was not run.

00:30 Video through the VPS works

Tailnet-only forwarder on VPS port 8900 (temporary unit video-hop-test, deploy/video-hop.ts). Blank data, four alternating rounds: direct 3.7-4.4 Mbit/s, via VPS 27-58. One real video range through it, using the existing Ted Lasso link: about 15 Mbit/s, first byte 0.8 s. Not yet used by the app. Applying it needs a code change and a server restart, so it waits for your OK. Whole-playback smoothness, VPS bandwidth limits, and other homes are untested. Undo: sudo systemctl stop video-hop-test on the VPS.

00:50 Route between homes

Plain traceroutes outside Tailscale show the same delay: about 81 ms Edmonton to Fort Saskatchewan and 77 ms back, leaving through large carrier networks instead of staying local. So Tailscale doesn't add that delay. Tailscale also carried 27-58 Mbit/s through the VPS, so it isn't the general limit, though UDP handling on this one route isn't ruled out. Order with the hop: Real-Debrid, mini PC, VPS, Mac. Real-Debrid still connects only to the mini PC. Nothing changed for this; the switch is on hold for your go-ahead.

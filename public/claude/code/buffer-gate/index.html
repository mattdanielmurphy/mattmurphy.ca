Buffer gate: Mattinee loads before it plays

01:15 Buffer gate on Mac, iPad and Streamer

You asked for a buffer that builds up before playback, a meter in the middle of the screen, an app that keeps watching the whole time, automatic fallback, and an honest "not ready yet" with a time when nothing can play smoothly.

The states

  1. Finding a copy. The spinner, as before.
  2. Filling. The first frame sits behind a centred meter. When the meter is full, it plays. A healthy copy takes a second or two.
  3. Playing. The app keeps measuring the download speed against the file's bitrate.
  4. Ran out. Same meter. It loads more before going on, 15 seconds' worth, doubling with each further stall, so it can't play two seconds and stop over and over.
  5. Too slow, no copy picked by hand. It moves to the next copy from the same spot, one at a time. A copy is judged after 6 seconds of downloading, and swapped if it would need more than 25 seconds to load.
  6. No copy works. "Sorry, this isn't ready yet", with the time. Loading carries on behind the message and it starts by itself.
  7. More than the device can hold. Same message, but it says so and waits for you: Play now or Go back.
  8. Picked by hand. "This copy needs a long wait", with Play now, Let Mattinee choose and Go back. It never moves on by itself.

How the prediction works

Loaded video plus what keeps arriving has to stay ahead of what's being played, and that's tightest at the very end. So the head start needed is the time left × (1 − speed ÷ bitrate), counting on 95% of the measured speed. A copy that keeps up needs only the minimum.

The speed comes only from the video being played. Nothing probes Real-Debrid, so the rule from the IP block holds.

Seconds when the buffer is full aren't counted, because the player has stopped reading and that says nothing about the line.

What each player does

  • Mac: mpv has this built in (cache-pause-wait), so the app only keeps that number honest. RAM read-ahead went from 150 MB to 512 MB.
  • Mac, long waits: a wait too big for RAM moves to a temporary file, if all that's left of the video fits with 10 GB to spare. mpv deletes the file at once, so nothing is left behind even after a crash.
  • iPad: VLC stops its download counters while paused, so held video creeps at 1/32 speed with the sound off, then jumps back to where it stopped. Read-ahead went from 128 MB to 256 MB.
  • Streamer: the player is paused while it loads, and every byte is counted as it arrives. Read-ahead is 192 MB, with the app allowed a larger memory limit.
  • Server: picks the next copy from what was measured, cached copies first, at most 4 tries. It sends the rules with each play, so they can be tuned without new apps (buffer.* tweaks).

Real-Debrid downloads

If every copy is still downloading on Real-Debrid, the message now gives Real-Debrid's own time left, from one request made only after a play found nothing ready.

Decisions

  • Switch at the stall, not before. Switching early throws away what's already loaded and causes the same pause, so the app plays out the buffer first.
  • A speed right at the bitrate gets a long wait, on purpose. A 2-hour film at exactly its bitrate shows about 6 minutes. Tune buffer.margin if that feels too cautious.
  • No disk buffer on iPad or Streamer yet. It needs a small local proxy on each. That's the same piece the background downloads need, so it belongs with that work.
  • The Mac only uses disk when it has to. mpv's file keeps growing with everything read, so using it always would write whole films to your disk.

Rejected: a speed test before playing (touches the links), and asking the server every second (a struggling line is the worst time to depend on it).

What was tested

Everything ran against a stand-in server at chosen speeds, with no Real-Debrid.

  • Mac: no window and no sound, so your test build wasn't touched. Fast start, slow copy to fast copy, not ready, Play now, picked by hand, and the disk hold all passed. The card's look wasn't seen on the Mac.
  • iPad: in the simulator. Fast start, automatic fallback, not ready, starting by itself after 84 seconds, a mid-film speed drop, Play now, and picked by hand all passed.
  • Streamer: in a private emulator. Fast start, automatic fallback and a mid-film stall passed. Play now and a hand-picked copy weren't tried there.
  • Rules: 13 server tests on copies and the Swift rules tests pass. tests/addons.test.ts has one failure in code this work didn't touch.

Not done, and risks

  • No real film on a real device yet. The Real-Debrid time left has only been tested against a fake answer.
  • The server hasn't restarted. Until it does, the apps use fixed rules and can't predict from file size. They still work.
  • The Mac TestFlight build is held so your current test isn't disturbed.
  • The commit skipped the iPad auto-install hook, because it can close the app. The iPad gets this through TestFlight.
  • Streamer installs itself through the usual GitHub build once the app is off screen.
  • Local files on the Mac go through the same gate, but load so fast it should never show. Not tested.

01:50 Slow starts on the Mac

You saw an IMDb tooltip over the player and wondered whether keeping IMDb warm slowed loading, and noticed loading got much slower once the song detector arrived, with a permission prompt every time.

What was really going on

  • The tooltip came from the Mattinee page sitting behind the player, not from the warmed IMDb page. The mouse was still reaching the page's tiles.
  • The IMDb page did start loading at the moment a video started, so a whole web page was competing with the video.
  • The song detector set up its audio tap on the app's main thread as the file opened. That can block the main thread, and a permission prompt would hold it until answered.
  • The repeated prompts came from local builds being signed differently every time, so macOS treated each as a new app. The signed test builds didn't prompt in the 15 minutes checked.

What changed

  • Song detector and IMDb page now wait until the picture is moving, and the detector's setup left the main thread.
  • The page behind the player is hidden while playing, and told to keep running, because it's what moves on to the next episode.
  • Face memory stops sending frames while the gate is closed.
  • Opening a copy is now watched: three looks without it opening moves to the next copy. Before, only a dead relay was caught at that stage, which is why a play could spin for 94 seconds.
  • Local builds sign with your Apple Development certificate.

Not proven yet

I haven't measured how much each of these cost, because that needs a real play in the real app. Each play now logs when the file opened, the first frame, when playback began and how long the song detector took. If next-episode stops working, the hidden page is the first suspect. The song detector now starts mid-playback, which might cause a tiny sound blip.

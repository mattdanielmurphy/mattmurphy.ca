Audio Hijack: Tyler hears himself through the ducker

14:20 What I understand and the fix

Matt asked (via the coordinator): say how much I understand of his call setup, then find a routing where the ducker's trigger (Tyler + Matt's mic) never reaches Mic FX, only the ducked music and Matt's mic.

I read the session straight from ~/Library/Application Support/Audio Hijack 4/Sessions.plist (session "Facetime Call copy", saved 20:00 UTC) and the Ducking block's own definition inside the app (Audio Hijack.app/Contents/Resources/markup/Blocks/Ducking.js). I did not touch the screen or change anything.

What the session does today

  • Music → Ducking (the source that gets lowered).
  • FaceTime (Tyler) → three places: a Channels block set to Kill Right → Recorder; the MacBook speakers; and the Ducking block (as the trigger).
  • MacBook mic (Matt) → a Channels block set to Kill Left → Recorder; and straight to Mic FX.
  • Ducking → Mic FX and the speakers.
  • Recorder (MP3 256k, ~/Music/Audio Hijack) → BlackHole 16ch.

So the recorder gets a two-sided file (Tyler on the left, Matt on the right), and BlackHole carries that same feed to whatever listens on it, which I take to be the call-transcript tool, with Audio Hijack's recording as the backup. Mic FX is the Loopback device FaceTime uses as its microphone, so it's what Tyler hears.

Why Tyler hears himself

The Ducking block isn't a sidechain in the usual sense. Its own hint text says: "Overlay audio will play through, while other sources have their volume ducked." The first source connected is the overlay (trigger), and once it passes the Overlay Threshold the block outputs it mixed in with the lowered music. Below the threshold it mutes the overlay. There's no setting to switch that off.

So Ducking → Mic FX sends Tyler back to Tyler (only when he's loud enough, which is why it may come and go). It also sends a gated second copy of Tyler to the speakers, on top of the direct FaceTime → speakers line.

A second issue: Matt's mic isn't connected to the Ducking block, so the music only ducks for Tyler, not for Matt.

The fix: put the trigger on one side and throw that side away

The Ducking block keeps left and right separate, so we can park the trigger on the left channel, the music on the right, and then delete the left after ducking. Everything stays inside Audio Hijack; no Loopback changes are needed.

  1. Music → Channels "Mono" → Channels "Kill Left" → Ducking. The music now lives only on the right.
  2. FaceTime and the mic → one Channels "Kill Right" block → Ducking, connected first so it's the overlay. Both voices are now only on the left, and both trigger the duck.
  3. Ducking → Channels "Copy Right" → Mic FX and the speakers. Copy Right overwrites the left (the trigger) with the right (the music), so only the ducked music comes out, on both sides.
  4. Keep mic → Mic FX directly so Tyler still hears Matt at full level.
  5. Keep FaceTime → speakers directly so Matt still hears Tyler, and the recorder chain as it is.

Trade-off: the music sent into the call becomes mono. FaceTime sends mono voice audio anyway, so Tyler won't hear a difference. Matt hears mono music on his speakers too; if he wants stereo music locally, a second plain Music → speakers path can't be ducked by this block, so I'd leave it mono.

Untested: whether the Ducking block measures the trigger level on the left side alone. It should (the trigger is just as loud on one side), but if ducking stops firing, lower the Overlay Threshold a little.

Options I rejected

  • Phase-invert Tyler to cancel him out. The Ducking block mutes the overlay below the threshold, so an inverted copy would be heard on its own at those times. Latency would also have to match exactly. Too fragile.
  • A second Ducking block. It has the same play-through behaviour, so it moves the problem instead of solving it.
  • Loopback channel tricks. Possible, but the Channels blocks do the same job in one place.
  • Audio Hijack scripting. Scripts can start/stop sessions and toggle blocks, but there's no need for automation here.

How I'd apply it, and undo

Two ways: (a) I drive Audio Hijack on screen (needs Matt's clearance banner, about 3 minutes of mouse use), or (b) Matt quits Audio Hijack and I edit the session file directly (back up Sessions.plist first). The overlay is "the first source connected", and the file doesn't clearly record which connection is first, so (a) is safer. Undo: the original "Facetime Call" session is untouched, and this is the "copy" session.

Paste this into your Claude: build apps on Matt's component kit (hud-kit)

You now have write access to the private GitHub repo mattdanielmurphy/hud-kit. Build your Mac apps on it directly instead of copying its conventions by hand. Read it before you design or write any UI.

What it's for. Your app can be complex inside (audio analysis, sorting, building drum kits) while its frontend stays simple: a window, menus, lists, a search picker, a few settings. hud-kit makes that simple UI polished and consistent with Matt's apps, in light and dark, so you spend your effort on the engine, not on window chrome.

Heads up. hud-kit is young and changes often: git pull it at the start of every session, and re-sync components into your app after. Some parts assume Matt's Mac: Tweaks.swift and the HUD slots read Hammerspoon paths (~/.hammerspoon/…), and his web previews use .test domains. Those are optional; skip them if you don't have them, and ask before you rely on one.

1. Get it and read it

gh repo clone mattdanielmurphy/hud-kit ~/projects/hud-kit

Read in this order: README.md (the catalog of every component, built by bin/catalog; never edit it by hand), CONTRACT.md (the rules every component follows), PLATFORMS.md (why web code plus a thin native shell per platform), AG_CONTEXT.md (recent decisions). Use bun, not npm.

2. The stack

  • Swift shell. A Mac app is a small native shell around a web page. Sources/AppWindow.swift is the window (one web view that draws its own toolbar, with the stoplights kept inside it), WebWindowBar.swift makes the toolbar strip drag the window, NoZoom.swift stops page zoom. AppCommands.swift holds every command in one list and builds the menu bar from it, each with its shortcut, so Help-menu search finds them. HUDWindow, FloatingPanel, GlassPanel, MenuBarCard and NativeMenu cover floating windows, menu bar cards and menus.
  • Web UI inside the shell. The visible parts (lists, settings, sheets, toasts, sliders, shelves, player bars) are plain JS and CSS in web/<name>/, loaded in the app's web view. No framework. Pieces that must be native (borderless windows, system volume, video) stay in Sources/.
  • Compile Swift in directly: swiftc … ~/projects/hud-kit/Sources/*.swift, no package needed. Copy web components into your app with bin/sync-into <app-dir> <components…>, which adds a "Copied from" header to each file. Never edit a copied file in the app; fix it in hud-kit and sync again.
  • Look for an existing component first. If the README has what you need, use it. If not, add it to hud-kit, not to your app.

3. The contract: base plus skin, five points

A component is a base (structure, behaviour, knobs, no colours or fonts) dressed by a skin (skins/moss, plain, synth, party). One base, many skins, never a fork: a new look is a new skin. Every component meets all five:

  1. Knobs declared in code. Every size, gap, width and timing is {v, min, max, step, note}, keyed <prefix>.<knob>. Web: NAME.KNOBS. Swift: knobs(prefix:). No magic numbers.
  2. Tuned live. Web: NAME.tune(tweaks, prefix). Swift: read the value each time you use it. A change shows within a second, with no reload or restart.
  3. Registers with Edit mode. EDIT.piece(el, {name, knobs}), skipped quietly if Edit mode isn't loaded.
  4. Skinned, not styled. Base CSS holds only geometry and layers and reads --<name>-* variables; the skin fills them.
  5. Catalogued, storied, tested. A web/<name>/README.md or a /// Catalog: line, a story, and a tests/<name>_test.*. tests/run.sh runs them all.

4. Colour, Tweaks, Edit mode

  • Colour by role, never hard-coded. tokens/tokens.json → bun tokens/build.ts writes each skin's CSS, plus Swift (tokens/out/Skins.swift) and Lua constants. Roles: --c-bg, --c-surface, --c-ink, --c-muted, --c-line, --c-accent, --c-danger, and --t-display / --t-body for type. Don't invent a colour: add a token that cites where it came from.
  • Tweaks. An app's feel (timings, fades, sizes) lives in one tweaks.json. Sources/Tweaks.swift seeds it from declared knobs and hot-reloads it, so tuning needs no rebuild.
  • Edit mode (web/editmode). A switch that turns an app's layout into drag handles (a sidebar width, a gap, a card size). Each handle writes the same tweaks.json knob, so the change persists. A web-view app with no server uses Sources/TweaksBridge.swift. Expose sizes and gaps as knobs so they can be dragged.

5. Self-update, light and dark

  • Self-update with a build stamp. Sources/SelfUpdate.swift, selfupdate/ and web/selfupdate/ show the version and build and offer Update, never mid-playback or mid-task. Read selfupdate/README.md before wiring it.
  • Light and dark, always. Light is the default; dark follows the system. Check both, in the studio and in your app.

6. How to design it: X-or-Y rounds

Design in small decisions, not finished mockups. Never make three or four full designs to compare.

  1. Decide one thing at a time. Each round is about five decisions, each with two options (X or Y) that differ in one thing only. Earlier picks carry into later rounds.
  2. Low-detail layout first. Start with plain wireframes (where the list, search and detail go), then behaviour, and leave the look (skin, colour, type) for last.
  3. Designer, then builder. One agent writes the decision round and a short spec.md once you've picked; a second builds from the spec out of hud-kit components; a reviewer checks the result in light and dark. Show the options before any app code.

7. Working in the repo

  • Run tests/run.sh after any change, and bin/catalog after adding or editing a component (--check tells you if the index is stale).
  • Stage and commit only your own files, and pull before you push: Matt's Claude edits the same repo.
  • Keep it plain Markdown and model-neutral. If you add a component other Slub apps could use, add a line to IDEAS.md in slub-hq.
